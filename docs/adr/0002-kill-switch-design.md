# Kill switch: hotkey + window-focus check, no mouse-jiggle

The HLA §9 proposes detecting user-reclaimed input via a `pynput.mouse.Listener` with the `injected` callback distinguishing our own clicks from real user input. **This design has a bug given the HLA's process-isolation choice (§5):** the MCP server runs in its own process, so events generated by `take_action()` calls are *not* injected from the agent process's perspective. The agent's listener will see every MCP click as user input and trip the kill switch on every action — the system never makes progress.

## Decision

V1's kill switch is:

1. **Primary trigger: global hotkey via pynput (`cmd+shift+escape`).** Hotkeys are out-of-band — no race with our own input events.
2. **Secondary check: window-focus verification before every action** via `atomacos` or `osascript`. If the target app is no longer frontmost, halt with `Aborted`. This catches the user clicking out to take over without pressing the hotkey.
3. **No mouse-jiggle in V1.** Detection of "real" mouse movement requires accurate event-source attribution, which the process-isolated design defeats. Deferred until we have a single-process MCP refactor or a Quartz HID event-tap implementation.

The one-action race window (in-flight actions complete before halt) is accepted; the success criterion is "halts within one action of the user reclaiming input," consistent with the HLA.

A `kill-switch-test` command runs a 30-second harmless loop and is the gate before any real session is run. Build-sequence step 5's pass/fail criterion uses it.

## Considered alternatives

- **Single-process MCP (drop process isolation).** Mouse-jiggle would work via `pynput`'s injection check. Rejected: gives up the HLA-stated isolation property to recover UX (mouse-jiggle) for a need already covered by hotkey + window-focus.
- **Quartz HID event tap.** Subscribes to OS-level events with originating-process attribution; fully accurate. Rejected for V1: more macOS-specific glue than is justified for a feature already adequately covered.

## Future revisit

Mouse-jiggle could return in V2+ if we (a) move to single-process MCP for other reasons, or (b) implement the Quartz event tap. Neither is on the current roadmap.
