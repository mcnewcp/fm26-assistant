# Agent

The computer-use agent that drives a target desktop application (Football Manager 26 in V1) by observing screenshots and operating mouse + keyboard. Single context for V1; spans the four-layer architecture in §2 of [the HLA](../../notes/architecture/01-HLAv1.md).

## Language

### Session lifecycle

**Goal**:
The user's top-level instruction for one session — e.g. "advance to the next match."
_Avoid_: prompt, query, request.

**Session** (synonym: **run**):
One execution of `Agent.run()` from receipt of a goal to a terminal state.
_Avoid_: task (overloaded), conversation (V1 has no back-and-forth).

**Step**:
One iteration of the agent loop — capture screenshot → plan → optionally ground → execute. The step counter is the loop budget.
_Avoid_: turn (planner-API ambiguous), iteration.

**Scenario**:
A markdown file describing how to handle a class of goals — when it applies, how to decompose, what UI knowledge is needed, what counts as done, and what conditions trigger a handoff.
_Avoid_: skill (Anthropic Skills overload), playbook, recipe.

**Default scenario**:
The single scenario the router falls back to when no specific scenario matches the user's goal. Lives at `scenarios/default.md`. Has wide latitude (no prescribed loop, no specific UI knowledge), declares only universal handoff triggers, and is the V1.0 deliverable before any specific scenario is authored. Models the "no skill applied" mode in Claude-Code-with-skills.
_Avoid_: generic scenario, fallback, base.

### Terminal states

A session ends in exactly one of four terminal states:

**Done**:
The planner declares the goal satisfied. Distinguished by `done_reason="goal_complete"`.

**Handoff**:
The planner detects a scenario-declared condition that demands user attention and halts with a surfaced reason (e.g. "Player X injured for 3 weeks"). Distinguished by `done_reason="handoff"`.
_Avoid_: alert, escalation, interrupt (overloaded with OS interrupts).

**Stuck**:
An unrecoverable orchestration-level failure halts the session. Set by orchestration with a `stuck_reason` enum: `budget_exhausted` (step counter hit `max_steps`), `model_unreachable` (planner / grounder API persistently failing after backoff), or `malformed_planner_output` (JSON mode failed twice consecutively).

**Aborted** (synonym: **kill switch**):
The user reclaims input via the `cmd+shift+escape` hotkey, or the target application is no longer the frontmost window before an action fires. Distinct mechanism — interrupts execution from outside the graph. See [ADR-0002](../../docs/adr/0002-kill-switch-design.md) for why mouse-jiggle detection is not a V1 trigger.

**Handoff trigger**:
A condition declared in a scenario's markdown that, when the planner detects it on screen, causes a handoff. V1's only specific handoff trigger is "a player on the user's team is injured" (declared in `advance_to_next_match`); see also **universal handoff trigger**.

**Universal handoff trigger**:
A handoff trigger that applies to *every* session regardless of which scenario is selected — declared once in the default scenario and inherited by all others. V1 has two: application crash / unresponsive state, and bizarre / unrecognized screen state. Specific scenarios may add their own triggers; they cannot remove universal ones.

### Layer 2 — model

**Operator**:
The Python protocol that wraps planner + grounder behind one interface. The orchestration layer never imports a vendor SDK directly; it receives an Operator via dependency injection.

**Planner**:
The Operator's "decide what to do next" half. Sees a screenshot, the goal, the scenario, recent action history, and notes; emits an `ActionPlan`. V1 default: NVIDIA Nemotron 3 Nano Omni 30B-A3B-Reasoning via NIM.
_Avoid_: planner LLM (the planner is itself a VLM), brain.

**Grounder**:
The Operator's "where on screen is X" half. Takes a screenshot and a UI description; returns coordinates. V1 default: Holo2-8B via mlx-vlm.
_Avoid_: grounder VLM, vision model.

**ActionPlan**:
The planner's output for one step. Carries action type, optional `target_description` / `text` / `key`, an optional `note`, and terminal flags (`done` with `done_reason` and `summary`).

**To ground (verb)**:
To resolve a `target_description` into screen coordinates via the grounder.

### Cross-step memory

**Note**:
A short text observation the planner attaches to any action — e.g. "Read board message: target = top half by Christmas; non-critical." Notes accumulate in `AgentState.notes` and are rendered into every subsequent planner prompt. They are the substrate for the final digest and for the planner's reasoning across steps.
_Avoid_: scratchpad, memory (overloaded), log entry.

**Final digest**:
The user-facing summary of a session, generated by one extra LLM call at end-of-session, derived from notes. Surfaced on `done`, `handoff`, and `stuck` (different framings per terminal state).
_Avoid_: report, summary (overloaded — the planner also produces a per-handoff `summary` in its ActionPlan).

**Action history**:
A plain-text log of past actions taken in the current session, capped at the most recent ~15 entries when rendered into the planner's prompt. Each entry is one line: `step N: <action> [→ result]`. Distinct from **notes**: action history records *what was done*; notes record *what was observed*.
_Avoid_: trace, log (both overloaded with observability concerns).

### Layer 1 — orchestration

**Scenario router**:
A LangGraph node (`select_scenario`) that runs once at session start. Inputs: the user's goal plus each scenario's `When to use` section. Output: a scenario name. Falls back to `default` when no specific scenario fits — never returns `no_match`. Implementation in V1.0 is hard-coded to return `default`; the LLM-based router is wired in V1.1 once `advance_to_next_match` exists.
_Avoid_: dispatcher, selector.

**System prompt preamble**:
The static portion of the planner's system prompt — same on every step, identical across scenarios. Contains: the planner's role, the four terminal states and how to declare them, the universal handoff triggers (parsed from `default.md` at startup — single source of truth), and the `ActionPlan` JSON schema. Concatenated with the per-session scenario markdown and a static postamble to form the complete system prompt.
_Avoid_: header, prelude.

## Relationships

- A **session** runs many **steps** until a **terminal state**.
- Each **step** invokes the **planner**; the planner emits an **ActionPlan**; the **grounder** is invoked only if the action requires coordinates; the action is executed against the target via the action layer.
- A **scenario** is selected once per session and shapes every **planner** prompt thereafter.
- **Notes** accumulate across **steps** and feed both subsequent **planner** prompts and the **final digest**.
- **Handoff triggers** are declared by the **scenario**; the **planner** detects them; orchestration terminates the **session** with a **handoff** state.

## Example dialogue

> **Dev:** "When the agent reads an inbox message during `advance_to_next_match`, what happens?"
> **Domain expert:** "The **planner** clicks into the message, reads it from the screenshot, and attaches a **note** to the next action describing what the message said. If it's a **handoff trigger** (e.g. an injury), the planner emits an `ActionPlan` with `done_reason='handoff'` and a surfaced reason instead of continuing."
> **Dev:** "And at the next match, what does the user see?"
> **Domain expert:** "The session reaches the match-prep screen, the planner emits `done_reason='goal_complete'`, and orchestration generates the **final digest** from accumulated **notes** — that's what the user reads."

## Flagged ambiguities

- "Stop" was used informally to mean both **handoff** (agent decides) and **kill switch** (user decides). Resolved: these are distinct mechanisms with distinct terminal states (`Handoff` vs `Aborted`). Reserve "stop" for casual speech; in code and docs, use the specific terminal-state name.
- HLA §7 says scenarios "mirror how Claude Code skills work" — that is a *comparison*, not a naming choice. Our term is **scenario**; "skill" refers only to the Anthropic Skills construct.
- "Planner LLM" / "Grounder VLM" suffixes appear in the HLA. Resolved: drop the suffix — the planner *is* a VLM, and the suffix invites confusion. Canonical names are **planner** and **grounder**.
- "Generic" and "default" were both used early for the no-match fallback scenario. Resolved: **default**. "Generic" reads as watered-down; "default" is positional (it's *the* one selected when nothing else applies) and matches the Claude-Code-with-skills mental model the agent is patterned after.
